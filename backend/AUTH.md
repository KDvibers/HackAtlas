# B2: сессии и личные данные

Реализация следует [OpenAPI](../api/openapi.yaml) и [семантике Starter](../api/README.md). Контракт не менялся. Реализованный B3 — удаление аккаунта, модерация и отдельная browser-session админка — описан в [MODERATION](MODERATION.md); opaque Bearer протокол B2 сохранён.

## Что подключено и зачем

- Spring Security 7.1.1 из BOM Spring Boot 4.1.1 проверяет доступ к личным маршрутам. API stateless: нет HTTP session, Basic, form login или cookie-аутентификации. CSRF исключён только для `/api/v1/**`; за его пределами защита остаётся включённой.
- Spring `Argon2PasswordEncoder` с Bouncy Castle `bcprov-jdk18on:1.86` хранит пароль как Argon2id с отдельной случайной солью. Стартовые параметры: 19 MiB памяти, 2 прохода, parallelism 1, соль 16 bytes, результат 32 bytes. Можно увеличивать memory/iterations через свойства; значения ниже этого минимума отвергаются при старте. Основание: [Spring Security](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html) и [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).
- Spring Validation проверяет формат email. Собственный небольшой JSON parser проверяет поля строго по контракту: без преобразования чисел в строки, дублирующихся ключей, лишних полей или обрезания пароля. Тело register/login/PATCH ограничено 16 KiB, включая запрос без Content-Length.
- PostgreSQL и Flyway хранят пользователей/сессии (V3), интересы/закладки/личные отметки (V4). Существующие миграции не изменены. Параметризованные запросы Spring JDBC удобны для атомарного `ON CONFLICT`; каталог продолжает использовать JPA и его общий расчёт статусов.

Email приводится к нижнему регистру и очищается от внешних пробелов. Пароль сохраняет все пробелы и Unicode; ограничения длины считают Unicode code points. Пароль не хранится и не возвращается в исходном виде.

## Жизнь сессии

`POST /auth/register` или `POST /auth/login` возвращает `tokenType=Bearer`, `accessToken`, `expiresAt`, `user`. Ответ имеет `Cache-Control: no-store`. Токен — 32 случайных bytes из `SecureRandom`, представленные как Base64 URL без padding. В `auth_session` записывается только SHA-256 токена, идентификаторы, время создания/истечения/отзыва. SHA-256 применяется к случайному токену; пароль защищён Argon2id.

В каждом личном запросе нужен `Authorization: Bearer <accessToken>`. Принимается ровно один заголовок. Query, JSON, cookies и Basic не дают доступ. Проверка читает PostgreSQL каждый раз: отозванная сессия или `expiresAt <= now` возвращает 401. `POST /auth/logout` отзывает только текущую сессию, возвращает 204; её последующее использование даёт 401. Другие сессии того же пользователя продолжают работать.

Срок абсолютный, по умолчанию 30 дней; `HACKATLAS_SESSION_TTL` задаётся ISO-8601 Duration, например `P7D`. Обращения к API не продлевают срок. JWT, refresh endpoint и автоматическое обновление токена отсутствуют. При 401 клиент предлагает повторный вход.

## Регистрация и ограничения попыток

Регистрация закрыта по умолчанию. Для private dev/test нужны одновременно профиль `dev` или `test`, отсутствие `prod` и `HACKATLAS_REGISTRATION_ENABLED=true`. Даже случайное включение флага вместе с `prod` не открывает регистрацию. Это не публичный запуск: verification/reset остаются условием отдельного согласованного изменения контракта.

Auth limiter считает попытки register/login по IP и нормализованному email:

| Свойство | По умолчанию |
|---|---|
| `hackatlas.auth.rate-limit.window` | `PT15M` |
| `hackatlas.auth.rate-limit.ip-limit` | 30 |
| `hackatlas.auth.rate-limit.account-limit` | 10 |
| `hackatlas.auth.rate-limit.max-keys` | 10000 |

Счётчики защищены от конкурентных запросов. При заполнении памяти активные записи не вытесняются: новый ключ получает 429. Ответ содержит `Retry-After` в секундах. Forwarded/X-Forwarded-For не принимаются на доверие; `server.forward-headers-strategy=none`. При будущем reverse proxy нужна явная политика доверенных прокси.

Отдельный `hackatlas.auth.password-concurrency=4` ограничивает одновременные вычисления Argon2 во всём процессе. При занятом лимите нет очереди тяжёлых операций: ответ 429 и `Retry-After: 1`. Разрешение освобождается и после исключения. Это ограничивает основную память Argon2 примерно 76 MiB при стартовых параметрах, без учёта прочих расходов JVM.

Это ограничитель одного процесса: перезапуск сбрасывает окна, несколько экземпляров не разделяют лимиты. Распределённый limiter/внешняя anti-abuse защита требуют решения перед масштабированием и публичной регистрацией. Redis и отдельная библиотека limiter сейчас не добавлены: ограниченный синхронизированный счётчик покрывает текущий один экземпляр и проверяется конкурентными тестами.

Воспроизводимые тесты могут фиксировать Clock; в таком режиме не движутся ни сроки сессий, ни окна limiter. Для ручной работы не задавайте `HACKATLAS_DEMO_AS_OF` без необходимости. Успешный и неуспешный login расходуют лимит. Неизвестный email проверяется против dummy Argon2 hash и получает такое же сообщение 401, как неверный пароль.

## Профиль и личные списки

ID пользователя берётся только из проверенной серверной сессии. В запросах нет возможности выбрать чужой аккаунт. `PATCH /me` использует allowlist полей; email, admin и security role изменить нельзя. `roleLabel` — разрешённая подпись в профиле, она не выдаёт прав.

Отсутствующее поле сохраняет прежнее значение. `null` разрешён только для city/countryCode/roleLabel. `interests` заменяет весь список, проверяется по `catalog_tag.interest_allowed`; неизвестные ID и дубли отвергаются. Изменения транзакционные; параллельные PATCH одного пользователя блокируют строку аккаунта, предотвращая потерю других полей.

Сохранения и отметки независимы. Уникальные ключи `(user_id, hackathon_id)` делают повторные PUT безопасными; повторный PUT отметки сохраняет исходный `markedAt`. DELETE возвращает 204 и при отсутствии записи. Серверные списки показывают только опубликованные события, включая ended/cancelled; draft/archived скрыты. Счётчики профиля соответствуют доступным спискам. Порядок: время сохранения/отметки DESC, затем UUID ASC. Пагинация принимает большой неотрицательный page и возвращает пустую страницу без переполнения.

Для переноса гостевых закладок клиент выполняет отдельный PUT каждого ID, фиксирует подтверждённые успехи и повторяет остальные. Неизвестный/скрытый ID даёт 404 только на PUT; уже перенесённые записи не дублируются. Смена аккаунта не переносит личные данные автоматически.

## Проверки и запуск

Команды находятся в [backend README](README.md) и [B2 checks](../scripts/b2/README.md). Testcontainers создаёт временную настоящую PostgreSQL; JUnit проверяет HTTP, SQL-ограничения, изоляцию, сроки/отзыв, strict JSON и лимиты. Экспорт HTTP проходит JSON Schema validation по неизменённому OpenAPI; accessToken в экспорте заменяется тестовым placeholder. Bruno проверяет пользовательский поток у собранного JAR. B1 Schemathesis и существующие проверки каталога сохраняются.

В логах ошибок остаются класс исключения и requestId. Пароли, токены, Authorization, SQL values и входные JSON не логируются. Локальные отчёты/экспорты находятся в игнорируемом `backend/target/`.
