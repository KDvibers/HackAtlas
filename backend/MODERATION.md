# B3: модерация, редактор каталога и удаление аккаунта

Реализация следует неизменённым [OpenAPI](../api/openapi.yaml) и [правилам Starter](../api/README.md). B3 добавляет три ранее предусмотренных JSON endpoint и отдельные HTML-страницы администратора. Запуск приложения и PostgreSQL описан в [backend README](README.md), сессии мобильного API — в [AUTH](AUTH.md), статусы каталога — в [CATALOG](CATALOG.md). Deployment B4 остаётся отдельным этапом.

## JSON API для мобильного приложения

Все пути ниже начинаются с `/api/v1`. Нужен заголовок `Authorization: Bearer <accessToken>` действующей opaque session. Browser cookie администратора не даёт доступ к JSON API; JWT и refresh endpoint не добавлены.

| Операция | Тело JSON | Успех |
|---|---|---|
| `POST /suggestions` | `url`: HTTPS-ссылка; `comment`: строка до 2000 символов либо `null`. Оба поля обязательны | `202`, receipt с UUID и `status=PENDING` |
| `POST /hackathons/{id}/reports` | `reason`: `DATES`, `LINK`, `PRIZE`, `ELIGIBILITY`, `DUPLICATE` или `OTHER`; `message`: строка от 5 до 2000 символов | `202`, receipt с UUID и `status=PENDING` |
| `POST /me/delete-account` | `password`: текущий пароль, от 1 до 256 символов, без trim | `204` после успешной проверки пароля и удаления |

Пример предложения, использующий демонстрационный адрес:

```json
{
  "url": "https://example.org/event",
  "comment": null
}
```

`PENDING` означает поступление в очередь. Предложение не создаёт опубликованную карточку, а сообщение об ошибке не изменяет событие автоматически. Отчёт принимается только для доступного опубликованного события; неизвестный, draft или archived ID возвращает `404`. Повтор POST предложения/сообщения создаёт новое обращение: ключ идемпотентности для этих операций контрактом не предусмотрен.

Проверка URL проверяет синтаксис HTTPS, наличие host, допустимый порт и отсутствие логина/пароля в адресе. Она не разрешает DNS, не скачивает страницу и не следует redirect. Адрес с IP или внутренним host сам по себе не запускает сетевое обращение сервера. Проверка синтаксиса не подтверждает достоверность сведений: источник проверяет человек.

Ввод обрабатывается строгим JSON parser: неизвестные и повторяющиеся поля, неверные типы, некорректный Unicode, превышение длины и JSON body больше 16 KiB дают `400`. Ошибки JSON API используют `application/problem+json` из Starter; недействующая сессия даёт `401`, ограничения попыток — `429` с `Retry-After` в секундах.

## Локальная подготовка администратора

Административные права хранятся отдельно в `hackatlas.admin_access`. Регистрация, изменение `roleLabel` и DEMO seed не выдают эти права. Миграции V5/V6 создают только таблицы и ограничения, без аккаунтов и автоматических grants.

1. Подготовить локальную БД по [infra README](../infra/README.md) и запустить backend из каталога `backend/` с профилем `dev`. Для создания собственного dev-аккаунта регистрация включается явно: `--hackatlas.auth.registration-enabled=true`. Без этого флага она закрыта; в `prod` она остаётся закрытой независимо от dev-флага.
2. Создать обычный аккаунт через существующий `/api/v1/auth/register` либо использовать уже имеющийся. Сохранить UUID аккаунта из ответа. Не создавать запись с паролем напрямую через SQL.
3. Оператор БД вручную проверяет выбранный аккаунт и выдаёт ему доступ. Ниже команды для интерактивного `psql`; `account_id` вводится при запросе и должен относиться к проверенному существующему аккаунту в нужной БД.

```sql
\prompt 'UUID существующего аккаунта: ' account_id

SELECT id, email, display_name
FROM hackatlas.user_account
WHERE id = :'account_id'::uuid;
```

После проверки выбранной записи оператор выполняет grant:

```sql
INSERT INTO hackatlas.admin_access (user_id)
SELECT id
FROM hackatlas.user_account
WHERE id = :'account_id'::uuid
ON CONFLICT (user_id) DO NOTHING
RETURNING user_id;
```

Если аккаунта нет, новая запись не создаётся; повтор grant также не создаёт дубликат. Не добавляйте персональные UUID, email, пароли, cookies или токены в репозиторий и SQL-миграции.

Для отзыва права оператор выполняет:

```sql
DELETE FROM hackatlas.admin_access
WHERE user_id = :'account_id'::uuid
RETURNING user_id;
```

Следующий административный запрос проверяет эту таблицу. Отзыв права или удаление аккаунта инвалидирует его существующую browser session при следующем запросе; перезапуск приложения не нужен. Изменяющие операции дополнительно проверяют доступ внутри транзакции и блокируют строки аккаунта/права в том же порядке, что и удаление аккаунта.

## Вход и защита HTML-редактора

Локальная страница — `/admin/login` на том же host и порту, где работает backend. В форме используются email аккаунта как `username`, исходный `password` и CSRF-поле `_csrf`. Успешный вход перенаправляет в `/admin`; неверный пароль и отсутствие admin-доступа возвращают одинаковое сообщение о неудачном входе. Bearer-токен не заменяет вход в редактор.

Spring Security использует отдельную цепочку browser authentication. Все изменяющие HTML-формы, включая login/logout, защищены CSRF. Thymeleaf добавляет скрытое поле токена; тестовый HTTP-клиент должен сначала получить страницу формы и сохранить cookie. Сессионный ID меняется при входе. `POST /admin/logout` закрывает browser session и удаляет cookie с правильным `Path=/admin`; это не вызывает logout мобильных Bearer sessions.

Cookie называется `HACKATLAS_ADMIN_SESSION`: `Path=/admin`, `HttpOnly`, `SameSite=Strict`; срок бездействия — 30 минут. По умолчанию `Secure=true`. В `prod` Secure принудительно сохраняется даже при смешанных dev/prod профилях или ошибочном property override. Только локальный профиль `dev` разрешает `Secure=false` для HTTP; HTTP-тесты задают это явно. Production HTTP нельзя использовать как обход этого правила; TLS и доверенные reverse proxy относятся к B4.

## Маршруты редактора

| Маршрут | Назначение |
|---|---|
| `GET /admin` | Список по 50 событий, `page` от 0, порядок `updatedAt DESC, id ASC` |
| `GET /admin/events/new` | Форма нового черновика |
| `POST /admin/events` | Создать черновик и открыть его страницу редактирования |
| `GET /admin/events/{id}/edit` | Открыть карточку |
| `POST /admin/events/{id}` | Сохранить поля полной HTML-формы |
| `POST /admin/events/{id}/verify` | Явно отметить проверку источника; требуется `sourceChecked=true` |
| `POST /admin/events/{id}/publish` | Опубликовать после review; требуется `reviewConfirmed=true` |
| `POST /admin/events/{id}/archive` | Архивировать без hard delete |
| `GET /admin/queue` | Первые 100 обращений `PENDING`, начиная с ранних |
| `POST /admin/queue/{id}/review` | Решение `RESOLVED` либо `DISMISSED` через поле `decision` |

Успешные POST форм перенаправляют на страницу карточки или очереди. Ошибка проверки полей возвращает `400`; при сохранении карточки форма показывает введённые значения и сообщение. Это отдельный интерфейс оператора, а не расширение mobile OpenAPI.

## Содержание карточки и даты

Редактор изменяет только явный список полей:

- `title` — 1–200 символов, `shortDescription` — до 350, `description` — до 20000; `organizerName` — 1–160 и необязательный `organizerWebsiteUrl`.
- `format` — ONLINE/OFFLINE/HYBRID; `countryCode` — пусто либо две заглавные латинские буквы; `city` — до 100, `venue` — до 300.
- `officialUrl`, `sourceUrl`, необязательные `registrationUrl` и `rulesUrl`.
- `registrationStatus` и `eventStatus`, включая POSTPONED/CANCELLED.
- Дата начала, окончания и дедлайн регистрации: поля с префиксами `starts`, `ends`, `deadline` и суффиксами `Precision`, `Date`, `Time`, `TimeZone`.

Это сохранение полной формы, не PATCH: пустые необязательные поля очищаются. Неизвестные/повторяющиеся имена полей отвергаются. Slug, темы, призы, условия участия, этапы и другие не представленные в форме данные существующей карточки сохраняются. Новый черновик получает UUID/slug, `WIREFRAME`, неизвестный приз и неизвестные необязательные условия; фиктивные суммы и ограничения не добавляются. Метка `isDemo` существующих fixtures остаётся неизменной.

Для неизвестного времени выбрать пустую точность и очистить дату, время и пояс. Для `DATE` обязательна только дата: время и instant остаются `null`, IANA zone может быть известна или отсутствовать. Для `MINUTE` нужны дата, время `HH:mm` и IANA zone; сервер сам вычисляет согласованный UTC instant. Невозможное или неоднозначное время при переходе DST отклоняется: сервер не выбирает offset молча. Окончание раньше начала также отклоняется. День без времени не заменяется на 00:00 или 23:59.

Сначала нужно сохранить изменения формы, затем выполнить отдельные действия проверки/публикации:

1. Вручную проверить официальный сайт и источник; оба адреса должны быть корректными HTTPS-ссылками.
2. Подтвердить «Я вручную проверил сведения» и выполнить `verify`. Только это действие устанавливает `lastVerifiedAt`; само поле `updatedAt` оно не обновляет.
3. Проверить сохранённую карточку и выполнить `publish` с подтверждением review. Публикация требует непустых официального URL и source URL, отметки проверки и повторно валидирует редактируемые данные.

Обычное редактирование обновляет `updatedAt` и сохраняет прежнее время проверки. Изменение `officialUrl` или `sourceUrl` очищает `lastVerifiedAt`: прежняя проверка не относится к новому адресу. Публикация и архив также меняют `updatedAt`; при повторной публикации первоначальный `publishedAt` сохраняется.

Изменение уже опубликованной карточки сразу отражается в публичном API и saved-ответах. POSTPONED/CANCELLED передают перенос/отмену без удаления закладок. Архивная карточка скрывается из публичных результатов и доступных личных списков, но её запись и связи не удаляются. Вычисление статусов по датам продолжает работать по правилам [CATALOG](CATALOG.md).

## Очередь и лимиты

Очередь показывает `PENDING` по `created_at ASC, id ASC`, максимум 100 записей. Текст и ссылки выводятся через HTML escaping; URL не открывается сервером. Оператор отдельно исправляет/создаёт карточку и затем отмечает обращение как `RESOLVED`, либо отклоняет как `DISMISSED`. Решение меняет статус/время review и добавляет аудит в одной транзакции; автоматической публикации нет. Повторное решение по уже обработанному обращению возвращает `404`.

Suggestions и reports делят отдельные окна ограничений:

| Свойство | По умолчанию |
|---|---|
| `hackatlas.moderation.rate-limit.window` | `PT1H` |
| `hackatlas.moderation.rate-limit.ip-limit` | 60 |
| `hackatlas.moderation.rate-limit.account-limit` | 20 |
| `hackatlas.moderation.rate-limit.max-keys` | 10000 |

Admin login и повторная проверка пароля удаления используют общие auth-лимиты вместе с регистрацией/входом: IP 30 и нормализованный email 10 за 15 минут. Для удаления IP проверяется до разбора тела, account — перед проверкой пароля; admin login также ограничен по IP/account. Общий `hackatlas.auth.password-concurrency=4` ограничивает одновременные вычисления Argon2. Полные настройки — в [AUTH](AUTH.md).

Счётчики работают в памяти одного процесса и сбрасываются при перезапуске; активные записи не вытесняются при заполнении. Несколько экземпляров не имеют общего счётчика. `Forwarded`/`X-Forwarded-For` не считаются доверенными. Для масштабирования нужна отдельная согласованная политика B4. Фиксированный DEMO Clock замораживает и окна лимитера; для ручной редакторской работы его задавать не следует.

## Удаление, аудит и проверка реализации

Удаление аккаунта требует действующую Bearer session и правильный текущий пароль. Операция транзакционно удаляет аккаунт, все его opaque sessions, интересы, закладки, отметки заявок, отправленные предложения/сообщения и admin-доступ. Ошибка пароля не удаляет данные. После успешного `204` старые токены получают `401`, а административная browser session теряет доступ при следующем запросе. Повтор с удалённой сессией также возвращает `401`. События каталога удалением аккаунта не удаляются.

`admin_audit` содержит только UUID записи, nullable actor ID, код действия, nullable event ID и время. Содержимое форм, URL обращений, пароли, токены и email туда не копируются. При удалении аккаунта прежние actor ID становятся `null`; новая запись `ACCOUNT_DELETED` не содержит actor/event ID. Операторские SQL-grants не создают запись прикладного аудита автоматически. Правила доступа, хранения, удаления и ограничения резервных копий описаны в [PRIVACY](../docs/PRIVACY.md); настройки production retention/backups не считаются выполненными этапом B3.

Проверки выполняются командами из [backend README](README.md): Maven `verify` с настоящей PostgreSQL/Testcontainers, сверка реальных HTTP-ответов с общим OpenAPI и [B3 runner](../scripts/b3/README.md) с [Bruno-коллекцией](../tools/bruno-b3/README.md). HTTP-тесты покрывают API, изоляцию пользователей, CSRF, разграничение Bearer/browser session, отзыв admin-доступа, редактор/даты/источник и последствия удаления. Smoke удаления должен использовать только специально созданный одноразовый аккаунт и отдельную тестовую БД. Итог конкретного прогона фиксируется в [STATUS_BACKEND](../docs/STATUS_BACKEND.md), а не предполагается по наличию тестов.
