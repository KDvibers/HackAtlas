# Общий план HackAtlas

Backend ведёт пользователь, Android/iOS-клиент — напарник. План сохраняет этапы Starter и разделяет работу на проверяемые результаты. Он не означает, что реализация уже начата, и не разрешает выполнить все этапы одним заходом.

Фактическая готовность записывается отдельно в [STATUS_BACKEND](STATUS_BACKEND.md) и [STATUS_MOBILE](STATUS_MOBILE.md). На старте каждого задания проверить эти статусы, текущую ветку и существующий код. Пользователь может поручить один этап или пакет, например B0/B1 либо M0/M1: внутри пакета выполнять промежуточные проверки и продолжать без повторного разрешения, а на согласованной границе — отчёт и остановка. Обязательное визуальное утверждение M1 сохраняется. Push и создание PR выполняет пользователь, ветки — без префикса `codex`.

Пять принятых продуктовых ориентиров из [PROJECT](PROJECT.md): источник и свежесть данных, отдельные дедлайн заявки и дата начала, быстрые фильтры, offline snapshot сохранённого события и честная личная отметка подачи заявки. Остальные гипотезы исследования не становятся обязательными функциями этого плана.

## Технологическая основа

Выбор направления описан в [TECHNOLOGY_DECISIONS](TECHNOLOGY_DECISIONS.md), обоснование и альтернативы — в [исследовании](research/2026-10-20-technology-research.md). Точные совместимые stable-версии закрепляются при B0/M0 в toolchain-файлах и конфигурации сборки; номера релизов из исследования не являются lockfile.

| Дорожка | Минимальная основа | Что подключать по мере необходимости |
|---|---|---|
| Backend | Java 21, Spring Boot 4.x/BOM, Maven Wrapper, Spring MVC, Spring Data JPA, PostgreSQL 17, Flyway, явные DTO и JUnit/PostgreSQL tests | Spring Security для B2; Thymeleaf для B3; rate limiting для auth/moderation, кандидат — Bucket4j |
| Mobile | Kotlin Multiplatform + Compose Multiplatform, один shared-модуль и Android/iOS hosts, Gradle Wrapper, coroutines/StateFlow, kotlinx.serialization, ручной DI | Ktor с OkHttp/Darwin для M2; несекретные settings/guest IDs, кандидат — multiplatform-settings; платформенные адаптеры и SecureTokenStore |
| Совместная проверка | `api/openapi.yaml`, `api/README.md`, общие fixtures, существующий contract validator, Git/PR review | Плановые инструменты: Gitleaks CLI на B0; Bruno и Schemathesis на B1; oasdiff при первом изменении API |

Для PostgreSQL tests выбран основной подход — Testcontainers с согласованным lifecycle; service container допустим как обоснованная замена. Не держать два разных механизма без необходимости. Для mobile выбрать один механизм навигации после небольшой проверки Android/iOS; дополнительную SQLite-библиотеку и Coil подключать только при сценариях, которым недостаточно простого локального хранения и встроенных иллюстраций.

Без Mac допускаются предварительный выбор для Android/common и визуальная приёмка Android по правилам TECHNOLOGY_DECISIONS. Непроверенная iOS-совместимость остаётся открытым пунктом; доступная часть работы продолжается, полная приёмка обеих платформ не объявляется завершённой.

ArchUnit может проверять несколько важных границ после появления слоёв. MapStruct, jOOQ, Spring Modulith и pg_trgm/FTS не являются условием старта: их польза должна быть подтверждена повторением кода, сложностью запросов или измерениями. В MVP не добавляются микросервисы, Redis/Kafka, серверный push, чат, команды или LLM-рекомендации.

## G0 — общий старт

**Общий результат:** оба разработчика используют один репозиторий, одну версию Starter API и один утверждённый [визуальный референс](../design/reference/approved-reference.png).

- Проверить, что у обоих одна согласованная основа `main`; не создавать второй API или новый remote вместо существующего.
- Вручную сверить API и семантику дат, unknown/null, сохранений, self-reported отметок и opaque sessions. Изменение договора — отдельный PR с причиной, fixtures и подтверждением обоих разработчиков.
- Проверить доступные SDK, Docker и доступ к Mac/Xcode; неизвестное записать как непроверенное. Указать реальные аккаунты и области владения, не угадывать handle напарника.

**Готово, когда:** общие файлы доступны обоим, contract-check проходит, каждый подтвердил используемый контракт и свою область. Подготовленная спецификация не доказывает готовность сервера.

**Стоп:** согласовать следующие задания B0 и M0/M1. Вложенные промпты не разрешают автоматически перейти к реализации.

## Как две дорожки идут параллельно

| Контрольная точка | Пользователь — backend | Напарник — mobile | Условие перехода |
|---|---|---|---|
| Сборочная основа | B0: серверный каркас и БД | M0: общий клиент и hosts | Каждая сторона воспроизводит свою сборку; неизвестная iOS-готовность явно отмечена |
| Первые проверяемые результаты | B1: три публичных GET и реальные ответы | M1: каталог, детали и профиль на fixtures | API проходит проверки; M1 получает явную визуальную приёмку |
| Публичная интеграция | B2 можно вести после приёмки B1 | M2 подключает B1 и гостевые сценарии | M2 зависит от B1 и утверждённого M1, но не от готовности auth |
| Личные и редакторские сценарии | B3 после B2: admin, moderation, удаление аккаунта | M3 подключает B2; формы reports/suggestions — после B3 | Никаких имитаций успеха неготового endpoint; личные данные изолированы |
| Проверка выпуска | B4: разрешённый staging и эксплуатационные проверки | M4: Android/iOS, release-конфигурация и общий smoke | Публичный запуск только после предрелизных условий и отдельного разрешения |

Backend не ждёт готового UI для B0/B1; напарник не ждёт сервера для M0/M1. Работы внутри M3, не зависящие от B3, можно вести отдельно. B4 и M4 завершают совместную проверку; доступный staging не заменяет проверки на устройствах.

## Backend: задачи пользователя

### B0 — воспроизводимая основа

**Вход:** завершённые для серверной работы договорённости G0.

Создать Java 21/Spring Boot каркас с Maven Wrapper, отдельной PostgreSQL, Flyway, dev/test/prod-конфигурацией и минимальным health. Подобрать stable-версии через Boot BOM, учитывать Jackson 3, актуальные starters и PostgreSQL-модуль Flyway. Описать команды PowerShell и bash. В CI сначала перенести существующий contract-check и сборку backend; использовать Gitleaks CLI с redaction для поиска секретов.

**Критерии готовности:**

- Wrapper собирает проект на Java 21; версии и команды записаны в `backend/TOOLCHAIN.md`.
- Соединение с PostgreSQL 17 и миграции проверены на чистой БД и повторном запуске; Hibernate использует `ddl-auto=validate`.
- Базовые tests реально выполнены; отсутствие Docker не маскируется H2 или отключённым тестом.
- Секреты находятся вне Git; dev/test-данные не включаются в production; health не раскрывает внутренние параметры.
- Gitleaks scan выполнен с указанной областью проверки; его результат не объявляется полной гарантией отсутствия секретов.

**Контрольная точка:** зафиксировать результат B0 и перейти к B1, если он входит в порученный пакет; иначе остановиться. Auth, каталог и admin не объявляются готовыми по успешному запуску skeleton.

### B1 — настоящий каталог

**Вход:** принятый B0 и согласованный API. Mobile M1 может выполняться параллельно.

Реализовать `GET /api/v1/hackathons`, `GET /api/v1/hackathons/{id}`, `GET /api/v1/metadata/filters`. Использовать явные DTO/mappers, параметризованный поиск, AND-фильтры, стабильную сортировку и пагинацию. DEMO seed с общими IDs включается явно и идемпотентно. Подготовить небольшую Bruno-коллекцию и после запуска сервера проверить три публичные операции через Schemathesis в изолированном окружении с временной БД.

**Критерии готовности:**

- Реальные HTTP-ответы и Problem-ошибки соответствуют Starter; JSON проверен через фактический MVC mapper, включая обязательные null и decimal-string.
- PostgreSQL tests покрывают поиск, диапазоны, пагинацию, published/draft/archived, unknown-значения и доступность опубликованных ended/cancelled деталей.
- Даты DATE/MINUTE, timezone и статусы проверяются с управляемым Clock; точное время не выдумывается.
- Запросы списка проверены на лишние загрузки/N+1; публичные ответы не содержат личных flags.
- Bruno-сценарии воспроизводятся, результаты Schemathesis разобраны; эти инструменты дополняют tests сериализации, SQL и бизнес-правил.
- Напарник получает команды запуска, проверенный base URL для его окружения, запросы/ответы и список реально доступных операций.

Base URL может вести на локально запущенный backend через emulator mapping или доступную LAN. `localhost` телефона не означает компьютер разработчика. Предоставление такого адреса не разрешает публичный деплой, покупку сервера или раскрытие PostgreSQL. Удалённый staging — только после отдельного согласования.

**Контрольная точка:** принять B1 и передать его для интеграции M2. Завершение M2 не блокирует B2; B2 начинается, если входит в порученную работу, иначе — остановка с отчётом. Не добавлять новую модель JSON для удобства клиента без общего изменения договора.

### B2 — аккаунты и личные данные

**Вход:** принятый B1; M2 может продолжаться независимо от реализации auth.

Реализовать register/login/logout, GET/PATCH `/me`, saved и application marks по Starter. Spring Security проверяет opaque Bearer sessions: криптографически случайный token, hash в БД, абсолютный срок и отзыв. JWT, refresh endpoint и silent renewal не добавляются. Пароли обрабатывает настроенный adaptive PasswordEncoder; auth получает rate limits.

**Критерии готовности:**

- Два пользователя полностью изолированы; `/me` определяется principal, PATCH ограничен allowlist и различает отсутствие поля/явный null.
- Успешный logout возвращает 204; последующий защищённый запрос с отозванным либо истёкшим токеном — 401.
- Saved PUT/DELETE идемпотентны; повтор application PUT сохраняет исходный markedAt; закладка и личная отметка независимы.
- Проверены ограничения auth, формат 400/401/403/429, отсутствие токенов/паролей в логах и `no-store` при выдаче токена.
- Проверены серверные предпосылки guest import и смены аккаунта: повторные PUT, частичный успех серии запросов и изоляция данных. Напарнику переданы HTTP-сценарии для интеграции M3; готовый мобильный M3 не является условием приёмки B2. Production signup остаётся закрытым до предрелизных условий.

**Контрольная точка:** передать проверенные операции для M3; B3 выполнять только в пределах порученной работы. Удаление аккаунта и verification/reset не выдавать за реализованные заранее.

### B3 — обслуживание каталога

**Вход:** принятый B2. Формы мобильной модерации подключаются после готовности соответствующих операций.

Создать минимальную admin-only HTML-админку на Thymeleaf: draft/publish/archive, исправление дат, перенос/отмена, отметка проверки источника. Admin использует отдельную browser-session защиту с CSRF. Добавить suggestions/reports с лимитами и очередью PENDING, а также удаление аккаунта по текущему контракту.

**Критерии готовности:**

- USER не получает admin-доступ; публикация выполняется после review; suggestions/reports возвращают контрактный 202.
- Произвольные пользовательские URL не скачиваются автоматически; источник, updatedAt и lastVerifiedAt имеют разные значения.
- Удаление аккаунта повторно проверяет пароль, отзывает все сессии и удаляет профиль/личные связи; последствия для audit/backups описаны.
- Проверено, что ответы saved отражают отмену/изменение опубликованного события; напарнику переданы примеры для обновления snapshots и reminders в M3. Готовые мобильные напоминания не являются условием приёмки B3.

**Контрольная точка:** зафиксировать результат B3; B4 требует согласованного deployment. Предрелизные условия ниже обязательны до публичного открытия, но не запрещают закрытый staging. Email verification/password reset требуют отдельного совместного расширения OpenAPI до реализации на обеих сторонах.

### B4 — staging/release

**Вход:** согласованный состав выпуска и явное разрешение на конкретный staging/deployment; стоимость и инфраструктура не выбираются молча.

Подготовить HTTPS, раздельные окружения, миграции, минимальные health/readiness, секреты, логи без PII и backup/restore. Выбрать один эксплуатационный вариант по бюджету и готовности обслуживать его. Выполнять сквозные smoke-проверки совместно с M4.

**Критерии готовности:**

- Staging доступен по согласованному HTTPS URL; клиент использует нужное окружение без отключения TLS validation.
- Backup восстановлен в отдельную БД, данные и smoke-сценарии проверены; процедура и достижимые RPO/RTO записаны.
- Выполнены проверки миграций, безопасной конфигурации, секретов и зависимостей; есть понятные действия при неудачном выпуске.
- Для публичного открытия пройдены предрелизные условия и M4; ограничения внутренней беты не скрыты.

**Стоп:** отчёт о фактических проверках. Staging, production-публикация и публикация в магазинах — разные действия; одно разрешение не подразумевает остальные.

## Mobile: задачи напарника

### M0 — собираемый cross-platform каркас

**Вход:** договорённости G0, доступные SDK и информация о Mac/Xcode.

Создать KMP/Compose Multiplatform проект с Android/iOS hosts, Gradle Wrapper, shared UI/data interfaces и ручным DI. Подобрать совместимый stable toolchain и записать его в `mobile/TOOLCHAIN.md`/version catalog. Вынести строки в ресурсы, конфигурацию API URL — из UI.

**Готово, когда:** common/Android реально собираются, имеются команды запуска; iOS собран и запущен на доступном Mac либо явно остаётся непроверенным. Отсутствие Mac не мешает работе над common/Android, но не закрывает iOS-приёмку и не разрешает удалить iOS target.

**Контрольная точка:** зафиксировать результат M0; при порученном пакете M0/M1 сразу продолжить M1. Первый мобильный пакет работ ограничен M0/M1.

### M1 — визуальное ядро

**Вход:** рабочий M0, общий DemoRepository и утверждённый референс; B1 не требуется.

Реализовать настоящими Compose-компонентами тему, пиксельные заголовки, карточки, tab bar и три экрана: каталог, детали, профиль. Сделать небольшой образец типографики, проверить кириллицу/символы и записать источники/лицензии ресурсов. Выбрать один механизм навигации с проверкой возврата и состояния вкладок.

**Готово, когда:** доступны реальные screenshots собранного приложения, проведено сравнение трёх экранов с референсом и получено явное визуальное утверждение. Указать, какие платформы проверены; макет или screenshot генератора не доказывает готовность UI.

**Обязательный стоп:** до визуального утверждения не переходить к M2 и не размножать неподтверждённый стиль на остальные экраны. Android-приёмка не заменяет оставшуюся проверку iOS.

### M2 — основные сценарии

**Вход:** утверждённый M1; remote-интеграция требует принятого B1 и проверенного base URL.

Подключить Ktor, сериализацию и REMOTE repository; реализовать поиск/фильтры, гостевые saved, календарь сохранённых событий, browser registration и share. Разделить DEMO, REMOTE и offline-cache. Хранить IDs и небольшой snapshot сохранённых карточек/деталей со временем кеширования, чтобы к ним можно было вернуться без сети. Для этого сначала выбрать простое локальное хранение; SQLite добавлять, когда объём и запросы оправдают её. Полный offline-каталог в этот этап не входит.

**Готово, когда:** сценарий каталог → поиск → детали → saved → официальный сайт → возврат работает без потери состояния; сохранённые карточки/детали доступны после перезапуска без сети; loading/empty/error/offline различимы, кеш показывает свежесть. Пользователь видит источник, время его сверки и отдельные даты заявки/начала, а быстрые фильтры используют существующий API. Сбой сети не включает DEMO. DATE не получает выдуманный countdown, closed/cancelled/no-link не выглядят как активная регистрация.

**Контрольная точка:** передать результаты интеграции; M3 выполнять, если он входит в порученную работу, иначе остановиться. Login-wall для публичного каталога не добавлять.

### M3 — аккаунты и удобство

**Вход:** M2 и проверенный B2; reports/suggestions требуют B3. Не зависящие от B3 личные сценарии можно принять отдельно.

Подключить auth/profile, saved sync, подтверждаемый guest import и личную отметку заявки. SecureTokenStore использует iOS Keychain и Android ciphertext с ключом в Keystore. Добавить локальные reminders через платформенные adapters, forms reports/suggestions — к готовым операциям; экспорт в системный календарь только при необходимости.

**Критерии готовности:**

- Токен отправляется только своему API; expiry приводит к понятному повторному входу без refresh flow.
- После logout/account switch очищаются приватный кеш и соответствующие локальные reminders; данные аккаунтов не становятся гостевыми автоматически.
- Guest import требует согласия; локальные данные не стираются до подтверждённых серверных успехов. Сбой сети при logout не выдаётся за подтверждённый серверный отзыв.
- Browser click не создаёт application mark. Успешная отправка формы подтверждается ответом сервера.
- Reminders учитывают отказ в разрешениях, прошлые даты, timezone, отмену и перепланирование; выбранное пользователем время не становится официальным дедлайном.

**Контрольная точка:** принять результат M3; M4 выполнять в пределах порученной работы. Будущие verification/reset flows реализуются после согласования расширения контракта.

### M4 — качество и устройства

**Вход:** принятые сценарии M2/M3 и доступ к реальным устройствам; staging B4 используется после его разрешённого запуска.

Проверить Android и iPhone: каталог → поиск → детали → saved → браузер → возврат, а также два аккаунта, expiry/logout, slow/offline network и восстановление состояния. Проверить safe areas, клавиатуру, крупный текст, TalkBack/VoiceOver, contrast, размеры нажатий и доступность выбранных визуальных эффектов.

**Готово, когда:** записаны реальные device/build/test результаты, screenshots сопоставлены с утверждённым M1, проверена release-конфигурация. Android debug APK, iOS simulator build и проверка на физическом iPhone — разные результаты. Отсутствие Mac/iPhone оставляет соответствующие пункты открытыми; Windows-сборка их не заменяет.

**Стоп:** передать результаты для решения о выпуске. Signing, TestFlight и магазины выполняются только при доступном окружении и отдельной авторизации.

## Условия перед публичным запуском

Внутренний dev/staging с закрытой регистрацией не равен публичному выпуску.

1. Оба разработчика согласовали расширение OpenAPI для email verification и безопасного password reset, обновили fixtures и реализовали соответствующие серверные/мобильные сценарии. Почта действительно отправляется; одноразовые истекающие токены и отзыв сессий проверены.
2. Проверены account deletion, anti-abuse/rate limits, изоляция пользователей, privacy/security review, контакт поддержки и правила хранения данных. Production signup открывается только после этой проверки.
3. Production-каталог основан на проверенных источниках; DEMO отделён, неизвестные условия обозначены честно.
4. B4 подтвердил HTTPS, секреты, миграции и восстановление backup; M4 подтвердил пользовательский сценарий на Android и iPhone.
5. Пользователь отдельно разрешил конкретный публичный выпуск. Требования и подписи магазинов проверяются перед подачей; успешная модерация не обещается.

## Передача результата после каждого этапа

Каждая сторона обновляет только свой STATUS: этап, ветка/commit, изменённые пути, точные команды и результаты, непроверенные пункты и следующий отдельный шаг. Общие файлы/миграции координируются заранее.

Backend передаёт напарнику доступные операции, среду и base URL, пример запроса/ответа, способ запуска и ограничения. Mobile передаёт screenshots, платформы проверки, результаты интеграционных сценариев и конкретные вопросы к API. Ни работающий mock, ни прошедшая проверка fixtures не означают, что endpoint реализован.

Любое изменение общего API проходит ручное review обоих разработчиков до адаптации кода. Contract validator и дополнительные инструменты помогают review, но не утверждают изменение вместо людей.
