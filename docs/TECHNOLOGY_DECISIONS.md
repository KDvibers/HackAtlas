# Технологические решения HackAtlas

Принято направление: **20 октября 2026**. Основание — [исследование технологий](research/2026-10-20-technology-research.md) и поручение пользователя закрепить его выводы. Источники, лицензии и рассмотренные альтернативы остаются в исследовании; этот документ определяет, что принято, что планируется и что ещё требует проверки.

Выбор направления не означает установку всех библиотек из исследования. Реализация идёт по [ROADMAP](ROADMAP.md), в пределах текущего задания и [статуса backend](STATUS_BACKEND.md) или [статуса mobile](STATUS_MOBILE.md). Принятие плана само по себе не запускает B0/B1 или M0/M1.

## Принятая основа

| Область | Решение | Граница |
|---|---|---|
| Backend | Java 21, поддерживаемая stable-линия Spring Boot 4.x, Spring MVC | Один монолит с feature-пакетами; без микросервисов |
| Данные | PostgreSQL 17 с поддерживаемым minor, Flyway, Spring Data JPA | Схемой управляют миграции; API использует DTO, а не JPA entities |
| Сборка backend | Maven Wrapper, согласованные зависимости через Boot BOM | Точные версии и воспроизводимость подтвердить на B0 |
| Mobile | Kotlin Multiplatform + Compose Multiplatform для Android/iOS | Общий UI и бизнес-логика; мобильная реализация у напарника |
| Сеть и состояние mobile | Ktor Client: OkHttp на Android, Darwin на iOS; kotlinx.serialization, coroutines и StateFlow | Явные DTO и mapping; разделённые DEMO и REMOTE repository implementations |
| DI | Ручная сборка зависимостей | DI-framework не добавляется без конкретной потребности |
| Platform adapters | SecureTokenStore, BrowserLauncher, ShareService, ReminderScheduler по мере появления сценариев | Секреты отдельно от обычных settings; платформенные возможности не размазываются по экранам |

На B0 и M0 выбирается **совместимый stable-набор**, проверяется сборкой и фиксируется в manifests, wrappers и соответствующих toolchain-документах. Версии из раздела исследования «наблюдаемые releases» не являются принятым lockfile. Нельзя независимо брать самый новый релиз каждой библиотеки. Правила фиксации — в [TOOLCHAIN](TOOLCHAIN.md).

## Неизменные границы

- Канонический API — [api/openapi.yaml](../api/openapi.yaml) и семантика [api/README.md](../api/README.md). Старый Handoff и `contracts/` не используются.
- Авторизация — opaque Bearer sessions с абсолютным сроком и отзывом. JWT, refresh endpoint и refresh-token flow не вводятся. Spring Security должен обслуживать этот протокол.
- Неизвестные значения, точность EventTime, различие absent/null, decimal-string для денежных сумм и ошибки сохраняют контрактную семантику. Возможности генератора не являются причиной упрощать API.
- Утверждённый визуальный стиль сохраняется по [STYLE_LOCK](STYLE_LOCK.md): black/magenta/cyan, пиксельные заголовки и wireframe-графика. UI состоит из настоящих компонентов.
- Непроверенные события и тестовые профили остаются DEMO. Переход на сайт организатора не считается поданной заявкой.

## Инструменты по этапам

Это план подключения при наступлении соответствующего этапа, а не отчёт об установленном окружении.

| Когда | Инструмент / действие | Проверяемый результат |
|---|---|---|
| G0 → B0 | Сохранить [scripts/validate_contract.py](../scripts/validate_contract.py) и [инструкцию запуска](../scripts/README.md); включить текущую проверку в CI | OpenAPI 3.1, refs, fixtures и проектные правила продолжают проверяться; новый lint не заменяет этот валидатор |
| B0/B1 | Testcontainers с PostgreSQL; на B0 проверить миграции, на B1 запросы и репозитории | Один основной способ integration tests локально и в Linux CI; нужен работающий Docker. Service container допустим как обоснованная альтернатива |
| B0 | Gitleaks CLI с redaction | Поиск секретов в проверяемых файлах/истории; успешный scan не считается полной гарантией их отсутствия |
| B0 | Минимальный GitHub Actions CI: contract check и backend build/tests | Actions закреплены commit SHA, permissions минимальны; обязательная итоговая проверка действительно запускается для каждого PR |
| B1 | Небольшая Bruno-коллекция | Воспроизводимые запросы каталога, фильтров, деталей и ошибок; реальные credentials и локальные секретные окружения вне Git |
| Первое согласованное изменение API | oasdiff против принятой базы main | Видимые потенциальные breaking changes; проверить применимость к EventTime. Семантический review обеих сторон остаётся обязательным |
| B1, после появления работающего сервера | Schemathesis для трёх публичных операций на изолированном тестовом сервере и временной БД | Проверка реального HTTP-поведения по схеме; не замена тестам бизнес-правил, сериализации и SQL |

Не дублировать инструменты с одной задачей. Для Gitleaks выбран CLI: у Action-обвязки отдельные условия. GitHub secret scanning для приватного репозитория не считается автоматически доступной бесплатной заменой.

## Выбор после короткой проверки

Кандидат не становится обязательной зависимостью до проверки нужного сценария. Результат фиксируется здесь: что выбрано, почему, на каких targets и какими командами проверено.

| Задача | Кандидаты / исходная позиция | Критерий выбора |
|---|---|---|
| Навигация M0/M1 | Navigation 3 — первый кандидат; Decompose — альтернатива при потребности в component lifecycle | Smoke test: четыре tabs с сохранением back stacks, открытие детали, Back, восстановление состояния и iOS. После проверки выбрать один подход |
| Небольшие несекретные данные M2 | multiplatform-settings — кандидат для preferences и guest saved IDs | Проверить нужные targets и операции; не хранить токен, профиль целиком или полноценный offline-каталог в settings |
| Offline saved M2/M3 | Room KMP или SQLDelight, если объём и выборки перерастут простое хранение snapshots в файлах/settings | Объём offline-сценария, миграции, стабильная совместимая версия и реальные Android/iOS-сборки. Выбрать одну БД |
| Шрифты M0/M1 | Press Start 2P и Tiny5 — проверяемые кандидаты, не утверждённая типографика | TypographySpecimen: нужные кириллические/латинские glyphs, символы валют, читаемость и совпадение с референсом на обоих targets; проверить источник и лицензию, затем получить визуальное утверждение |
| OpenAPI codegen | Ручные DTO допустимы; генерация — отдельный небольшой эксперимент | EventTime, Prize, Detail, Profile; null/absent и условные схемы, fixtures и отрицательные случаи; common/Android и доступный iOS build |
| Изображения | Coil 3 только при реальных remote images | Польза для загрузки/кэша изображений; локальным M1-assets отдельная сеть не нужна |
| Дополнительный API lint/docs | Redocly CLI или Spectral при появлении конкретной задачи | Выбрать один основной инструмент; сохранить текущий validator |
| HTTP faults/mocks | DemoRepository достаточен для начала M1; WireMock или Prism при необходимости | Проверяемые задержки, сетевые ошибки или внешний HTTP mock, которые нельзя удобно покрыть текущими fixtures |

Принятый ориентир — доступ к сохранённому offline; полноценная локальная БД добавляется только при необходимости для согласованного сценария. Полный offline-каталог этим решением не утверждён.

Шрифты не добавляются в этот передаваемый комплект автоматически. Проверка glyph mappings в исследовании не заменяет визуальную приёмку.

Если macOS/Xcode недоступны, допускаются предварительный выбор кандидата для Android/common и визуальная приёмка Android-экранов. В STATUS_MOBILE и toolchain явно записываются непроверенная iOS-совместимость и необходимые проверки на Mac; это позволяет продолжать доступную часть M0/M1 и последующих согласованных этапов. Такой выбор не считается окончательно проверенным для обеих платформ и не закрывает iOS-условия выпуска.

## Эксплуатация и обновления

В B4.5 отдельно утверждена локальная проверка restic 0.19.1 (BSD-2-Clause),
операторского CLI для шифрованных backup/export snapshots. Java-зависимость,
серверный сервис или выбранное облако не добавляются. Пин, установка и команды —
[runbook архива](../infra/release/RECOVERY_ARCHIVE.md). Текущий официальный binary
имеет unresolved HIGH/UNKNOWN и inventory gap; для реальных данных он **не принят**.
Manual release readiness получает отдельную проверку нового инструмента;
[security report](research/2026-10-31-recovery-tool-security.md) сохраняет ограничения.

Для продолжения B4 выбран Trivy 0.76.1 с pinned official image и проверкой OS/Go/JAR inventories. Внешнюю готовность проверяет отдельный manual workflow `External release readiness`: он отказывает на HIGH/CRITICAL/UNKNOWN, неустановленных версиях пакетов, устаревшем JRE или неполных evidence. Docker socket сканеру не передаётся; отдельные архивы связываются с реально испытанными контейнерами. Maven OSV и обычный Backend CI сохраняются. Успех этих проверок не заменяет разрешение deployment/M4/privacy review. Подробности и ограничения — [security tools](../scripts/security/README.md).

Для локальной подготовки B4 26 октября 2026 выбран один проверяемый кандидат: Docker Compose, Caddy, Spring Boot и PostgreSQL. Его конфигурация и команды находятся в [release runbook](../infra/release/README.md). Это не выбор или покупка VPS: пользователь явно ограничил этап подготовкой и локальными проверками. Провайдер, бюджет, регион, внешний домен и production-требования к восстановлению пока не выбраны; managed application + managed PostgreSQL остаётся альтернативой при дальнейшем выборе инфраструктуры.

Первый уровень диагностики — ограниченный Actuator health, безопасные логи и базовые метрики через совместимый с Boot Micrometer. Публичный health не раскрывает внутренние детали. Для backup нужна проверка `pg_dump` и восстановления в новую БД с последующим smoke test; наличие файла backup само по себе недостаточно.

Dependabot — исходный кандидат после появления manifests: сгруппированные обновления, без automerge. Renovate — альтернатива при необходимости более сложных правил. **Включение bot PR требует отдельного решения пользователя**: действующее правило оставляет push и создание PR пользователю. Это не препятствует обычному локальному обновлению зависимостей в рамках задания.

Sentry, внешняя analytics и полноценный OpenTelemetry/metrics/logs/traces stack отложены до конкретной потребности. Не считать hosted-функции бесплатными из-за лицензии OSS-компонента и не отправлять реальные пользовательские данные в новый внешний сервис автоматически.

## Что отложено или вне MVP

- Kubernetes, service mesh, микросервисы, Redis и Kafka/RabbitMQ — вне текущего MVP. Измеренная потребность может стать основанием для отдельного пересмотра границ, но не разрешает добавить их автоматически.
- Отдельный search engine и outbox отложены до доказанной потребности в поиске или доставке фоновых событий и решения о соответствующем усложнении архитектуры.
- В B4.4 пользователь отдельно утвердил узкую `account_deletion_receipt` с операторской private выгрузкой. Это минимальная запись в одной транзакции для backup review, без worker/очереди/подтверждаемой независимой доставки; общий outbox остаётся отложенным. Ограничения и выбранный вариант — [дизайн B4.4](superpowers/specs/2026-10-30-deletion-history-design.md).
- MapStruct, jOOQ, Spring Modulith и DI-framework до заметного повторения или архитектурной потребности; небольшие ArchUnit-правила и rate limiter можно оценить на соответствующих B1/B2-сценариях.
- GraphQL, замена backend/auth на Firebase или Supabase — возможный пересмотр архитектуры, а не продолжение текущего плана.
- Серверные push-уведомления; сначала предусмотренные MVP локальные напоминания.
- Универсальный scraper, LLM-рекомендации, поиск команды, чат, оплата и собственная подача заявки организатору — вне текущего MVP.

## Как менять решения

Совместимые patch-обновления и обычные реализации внутри выбранного стека выполняются в рамках текущего задания без отдельного разрешения на каждый шаг: обновить фиксированные версии, выполнить подходящие проверки и отразить существенный результат в отчёте. Согласованные зависимости вроде Boot/BOM или Kotlin/Compose/AGP обновляются совместимым набором.

Для новой библиотеки, framework или технического направления назвать конкретную проблему, сравнить с текущим подходом и минимальной альтернативой, проверить короткий сценарий и лицензию, затем записать выбор и последствия в этот документ. Это лёгкое правило обоснования изменений, а не новый барьер для рутинной разработки. Если выбор влияет на общие файлы или работу напарника, его координируют до правок.

Смена утверждённого стека, протокола авторизации, API или дизайна требует отдельного согласования. API дополнительно проходит совместный review backend/mobile по [WORKFLOW](WORKFLOW.md). Общий план, исследование и примеры библиотек не отменяют эти границы.
