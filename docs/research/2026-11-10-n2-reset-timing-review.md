# Время ответа при проверке кода восстановления в закрытом N2

10 ноября 2026. Измерение на `main` `1f381a5`, кандидат `0.2.0-test.1`.

У `POST /api/v1/auth/password-reset/verify` воспроизвёлся локальный сигнал
времени ответа. С неверным кодом проверка выданного запроса занимала дольше
проверки идентификатора из ответа на запрос для неизвестного адреса во всех
36 парах. Статус, `Problem` за вычетом `requestId`, тип содержимого и `no-store`
совпали. Сценарий с правильным кодом выдал grant в каждом из трёх прогонов.

## Что измерялось

- Три запуска одного собранного JAR через `scripts/lifecycle/local.py` с
  `prepare`, `up`, `serve` и `down`. Каждый запуск использовал новый закрытый
  стенд с пустой PostgreSQL, Mailpit и обычными системными часами. WSL, Java 21,
  UID 1000 с доступом к Docker. HTTP шёл по loopback с настройками N2 по умолчанию.
  SHA-256 JAR `a890e4b983dde184a28ce1d8aa25498dd0d5b7a610945766cb9777f7b1601b30`.
- В каждом запуске четыре синтетических аккаунта и четыре неизвестных адреса.
  Оба запроса `password-reset/request` возвращали `202` с `challengeId`. Для
  аккаунтов доставка реального тестового кода подтверждалась через Mailpit.
  Проверка в паре получала одну и ту же заведомо неверную строку из восьми цифр.
- Два предварительных запроса прогревали соединение и исключались из выборки.
  Затем три раунда по четыре пары с перемешанным порядком пар и запросов внутри
  пары. Python измерял время от начала HTTP-вызова до чтения ответа целиком
  на одном persistent-соединении. Отдельно выполнен контроль с блокировкой
  строки аккаунта и контроль с правильным кодом. Штатный лимит проверки 30 на
  IP за 15 минут оставался включён. На запуск приходилось 29 проверок кода.

| --- | ---: | ---: | ---: |
| 1 | 12 | 5,037 | 3,789 |

Медиана разницы внутри пар — **1,406 мс**. Диапазоны пересекались
(3,835–6,749 мс и 2,559–4,986 мс). Несколько измерений приходились на один
идентификатор, поэтому пары не стоит считать независимыми. По этому прогону
нельзя оценить точность классификации отдельных запросов через HTTPS, прокси
или сеть. Учитывать нужно также квоты, срок действия запроса и задержки доставки.

При искусственном удержании блокировки строки тестового аккаунта примерно
250 мс проверка его запроса ждала снятия блокировки и заняла 254–255 мс.
Вызов для неизвестного адреса при той же удерживаемой блокировке занял
4,5–4,7 мс. Это контроль причины, а не модель обычного трафика.

## Почему пути различаются

Публичный `request` выдаёт идентификатор до фонового поиска адреса. Для адреса,
которому можно доставить письмо, worker сохраняет запись с кодом. Для неизвестного
адреса запись не появляется. На `verify` идентификатор без записи завершает путь
после поиска по хешу. Идентификатор с активной записью дополнительно блокирует
аккаунт и строку запроса, проверяет HMAC и сохраняет неудачную попытку. Именно
эта ветка ждала блокировку в контроле. [Сервис восстановления](../../backend/src/main/java/com/hackatlas/auth/lifecycle/LifecycleService.java#L58), [хранилище кодов](../../backend/src/main/java/com/hackatlas/auth/lifecycle/EmailActionStore.java#L98).

Затронута приватность адреса. По времени ошибки локально различались запросы,
для которых сервер создал пригодную к проверке запись. На её создание влияют
наличие адреса доставки, состояние аккаунта и обработка фоновой задачи.
Успешная доставка письма проверялась отдельно. Сигнал не раскрывает код и не даёт reset grant.
OWASP рекомендует сопоставимое время ответа для известных и неизвестных аккаунтов
при запросе восстановления. Здесь измерен соседний шаг `verify`, который нужно
учитывать вместе с публичным `request`. [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html#forgot-password-request).

## Что проверить перед публичным включением

Для закрытого клиента можно продолжать Task 3–6 по согласованной матрице.
Для общего выпуска стоит отдельно согласовать способ закрыть наблюдаемый
сигнал. Основной кандидат для обсуждения — связать поиск записи на `verify`
с непредсказуемым значением, доступным только получателю письма. Тогда публичная
квитанция `request` сама по себе не позволит попасть на путь с блокировкой записи.
Такой вариант требует совместного решения по формату письма, UX и контракту.
Подгонка минимальной задержки HTTP или добавление фиктивной работы в БД могут
сократить обычный разрыв, но блокировка из контроля показывает пределы такого
подхода. Их влияние на нагрузку и верхние перцентили пришлось бы проверять отдельно.

Критерии будущей проверки — одинаковая семантика ошибки при неверном коде,
сопоставимые распределения в целевом HTTPS-окружении и при конкурирующих запросах,
сохранение лимитов, срока действия и одноразовости кода. До выбора решения этот
отчёт фиксирует наблюдение, а не готовность публичного восстановления.

Локальные драйвер и обезличенные замеры сохранены в ignored `backend/target/`
как `run-n2-reset-timing-review.py` и `n2-reset-timing-review.json`.
В JSON записаны времена, порядок, SHA-256 и результаты контролей. Три временных
стенда завершены. Канонический валидатор и 13 примеров, 15 lifecycle-тестов
и повторная валидация 127 HTTP-ответов из сборки прошли.
