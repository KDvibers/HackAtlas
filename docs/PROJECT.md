# Продукт и архитектура

## Что строим
HackAtlas помогает находить хакатоны, понимать требования, сохранять события и переходить на официальную регистрацию. Первый целевой охват: Казахстан и подходящие международные online-события. Не обещаем полноту мирового каталога.

Один монорепозиторий. Друг делает общий Android/iOS клиент; пользователь — общий Java backend. Мобильные клиенты работают с одним сервером через HTTPS/JSON, а не подключаются непосредственно к PostgreSQL.

## Продуктовые ориентиры — закреплены 20 октября 2026

1. **Проверенный источник:** пользователь видит официальный источник и время последней фактической сверки. Редактирование записи само по себе не обновляет `lastVerifiedAt`.
2. **Понятные сроки:** дедлайн заявки и начало события показываются раздельно. Неизвестное время не дополняется выдуманным; DATE не получает точный countdown.
3. **Быстрый отбор:** пресеты «Онлайн», «Казахстан», «Регистрация открыта» используют согласованные фильтры. Страна проведения не равна eligibility, online не означает worldwide.
4. **Полезное сохранённое без сети:** небольшой локальный snapshot карточки/деталей с видимой свежестью. Сетевая ошибка не заменяется DEMO, личные кеши аккаунтов не смешиваются.
5. **Честный переход к организатору:** после браузера сохраняется состояние просмотра; «Я подал(а) заявку» остаётся добровольной личной отметкой. Клик по ссылке её не создаёт.

Эти ориентиры реализуются внутри утверждённой визуальной системы и по этапам [ROADMAP](ROADMAP.md). [TECHNOLOGY_DECISIONS](TECHNOLOGY_DECISIONS.md) фиксирует способы реализации; [исследование](research/2026-10-20-technology-research.md) хранит аргументы и будущие гипотезы, а не дополнительный обязательный scope.

## Зафиксированные решения
- Kotlin Multiplatform + Compose Multiplatform. Веб-прототип и Figma не являются кодом продукта.
- Java 21 + поддерживаемый stable Spring Boot 4.x, Spring MVC, JPA, PostgreSQL 17, Flyway, Maven wrapper.
- Общий API `/api/v1`, OpenAPI 3.1. Все неизвестные значения имеют явное nullable/unknown представление.
- Четыре нижние вкладки как в утверждённом фото: Главная, Календарь, Сохранённое, Профиль. На подробностях события — back и отдельный CTA, без обязательного tab bar.
- Первый язык интерфейса русский; строки вынесены в ресурсы для будущего перевода.
- Гостевой просмотр каталога без onboarding-wall и login-wall. Сохранения гостя локальные. После входа — синхронизация с аккаунтом.
- Регистрация на мероприятие — официальный внешний сайт через системный browser surface. Нажатие не доказывает подачу заявки или отбор.
- «Я подал(а) заявку» — личная отметка, отдельная от состояния набора организатором.
- Профиль непубличный. Данные о победах не выдумывать; в реальном профиле можно показывать достоверные счётчики сохранений, собственных отметок и интересов.

## MVP: функциональные блоки
Каталог и поиск; фильтры; подробности; закладки; календарь выбранных событий; профиль и вход/регистрация; официальная ссылка; локальные напоминания; состояние сети/загрузки/пустоты; предложение события; сообщение об ошибке; минимальная защищённая админка.

Календарь сначала показывает даты сохранённых событий и их дедлайны. Это не отдельный серверный календарь и не синхронизация с Google Calendar. Добавление в системный календарь и напоминания — через платформенные адаптеры после основного сценария.

## Не входит сейчас
Поиск тиммейтов, команды, чат, social feed, подписки, платежи, собственная регистрация у организаторов, рекомендации на LLM, массовый парсинг, регистрация домена, деплой без разрешения. Для будущих команд достаточно устойчивых ID пользователей/событий; пустые таблицы и экраны не создавать.

## Производственная достоверность
Фото — эталон внешнего вида, не источник настоящих мероприятий. Даты/суммы/профили из него демо. Наши fixtures тоже вымышленные и имеют `isDemo=true`. В production использовать официально проверенные источники, `lastVerifiedAt`, дату изменения записи; не считать обновление записи проверкой источника.

## Архитектурная простота
Backend — модульный монолит по feature-пакетам. Mobile — UI + state + repositories + DTO mapping + платформенные адаптеры. В начале достаточно ручного dependency injection, одного shared-модуля и двух host-приложений. Не создавать десятки модулей и абстракций без сценария использования.

## Приёмка продукта
Один и тот же сценарий должен работать на реальном Android и iPhone: каталог → поиск → событие → закладка → официальный сайт → возвращение без потери состояния. Две разные учётные записи не должны видеть личные данные друг друга.
