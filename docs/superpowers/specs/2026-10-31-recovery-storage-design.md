# B4.5: предложение по хранению резервных копий и истории удалений

Дата: 31 октября 2026. **Вариант B утверждён пользователем; разрешена локальная реализация.**

Фактические результаты и новые security blockers после реализации — в
[статусе backend](../../STATUS_BACKEND.md); исходные границы дизайна ниже сохранены.

## Основание и цель

B4.4 принят: [PR #17](https://github.com/KDvibers/HackAtlas/pull/17) слит в
`52d265e3f57c10a7c9e9b4ac5898edc01389a95c`,
[Backend CI](https://github.com/KDvibers/HackAtlas/actions/runs/41113186062) успешен.
Следующий пункт [статуса backend](../../STATUS_BACKEND.md) — независимое хранение,
доставка, доступы и сроки вместе с backup policy. В [ROADMAP](../../ROADMAP.md)
нет отдельного B5: B4.5 здесь означает предложенную часть подготовки B4.

Сейчас `backup.py` создаёт dump и SHA256, `export_deletions.py` — полный снимок
committed UUID удалений, а `prepare_restore_review.py` — неодобренный review.
Файлы приватные, но ни шифрование, ни доставка за пределы машины не реализованы.
Обычный backup содержит старое состояние receipts; восстановить только его
недостаточно для определения удалений, совершённых позднее.

Разрешение пользователя остаётся **«только подготовка и локальные проверки»**.
Цель предложения — проверить способ сохранения и извлечения этих файлов до выбора
облака. Локальная лаборатория не считается независимым offsite-хранилищем.

## Варианты

| Вариант | Сложность и стоимость | Поддержка и совместимость | Вывод |
|---|---|---|---|
| A. Существующие файлы и ручное копирование | Минимум нового кода; место и перенос обеспечивает оператор | Работает с B4.4, но шифрование, проверка доставки и учёт копий остаются ручными | Разумно остановиться здесь до выбора инфраструктуры |
| B. Restic для операторских архивов | Один внешний CLI; локальная проверка не требует покупки облака, удалённое хранение оплачивается по выбранной инфраструктуре | Шифрованные snapshots, проверка и восстановление; можно начать с Linux-каталога и позже проверить SFTP/S3. Java/API не меняются | Рекомендация автора для следующей локальной проверки |
| C. Отдельный сервис подтверждаемой доставки удалений | Новый протокол, сервис, отказоустойчивость, эксплуатационные расходы | Потребуется отдельно проектировать состояния удаления и восстановления при частичных сбоях | Не добавлять в этот этап; наличие двух хранилищ само по себе не даёт атомарности |

**Пользователь выбрал вариант B:** «Утвердить локальный вариант с restic и реализовать».
Restic принят только как операторский инструмент для этого локального этапа.
Вариант B сохраняет периодическую выгрузку B4.4; обещания нулевой потери истории нет.

## Предлагаемый локальный объём варианта B

1. Проверить официальный stable-релиз restic, лицензию и опубликованные checksums;
   закрепить проверенную версию. Не устанавливать глобально и не обновлять Java/BOM.
2. Использовать отдельный временный каталог Linux/WSL с синтетическими данными.
   Репозиторий restic, исходные файлы и каталог извлечения разделены. Пароль хранится
   отдельным private-файлом, не попадает в архив, аргументы команд, Git или логи.
3. Архивировать только явно выбранные завершённые dump/checksum/export и небольшой
   manifest: версия формата, исходное окружение/БД, тип набора, имена файлов, hashes
   и время операции. Не архивировать рабочий checkout, `.env`, ключи или произвольный
   каталог. Все перечисленные файлы проверяются до загрузки; незавершённый набор
   не объявляется пригодным для восстановления.
4. Поддержать два сценария: набор с backup и отдельный более поздний export удалений.
   История не должна сохраняться только при создании нового dump. Snapshot ID и
   результат проверки фиксируются явно; локальный manifest не является подписью
   и сам по себе не доказывает доверенность источника.
5. Восстанавливать по точному snapshot ID в новый private-каталог без перезаписи.
   Проверять состав, identity и hashes, затем использовать существующие B4.2/B4.4
   команды. Ни один новый helper не вызывает `approve_restore.py`, не меняет
   `historyComplete=false` и не утверждает полноту списка удалений.
6. Проверить чтение всех данных лабораторного репозитория через restic и реальное
   извлечение файлов. Успех загрузки, целостность архива и полнота истории удалений —
   три отдельные проверки, одна не заменяет другую.

Точные команды и формат manifest будут закреплены в implementation plan после
выбора направления. Вместо самостоятельной криптографии используется проверяемый
инструмент; на момент согласования возможность его применения здесь была
подтверждена документацией, а локальный эксперимент ещё предстоял.

## Приёмка после утверждения

- Реальные `pg_dump` и export из одноразовой PostgreSQL попадают в шифрованный
  локальный репозиторий и извлекаются с теми же bytes/hashes.
- Более позднее удаление сохраняется отдельным snapshot; восстановление старого
  dump использует более поздний export и остаётся в карантине до ручного review.
- Потеря источника после последнего export не объявляется безопасным восстановлением.
- Неверный пароль, повреждённые/недостающие файлы, неправильное окружение,
  незавершённое сохранение и занятый путь извлечения приводят к отказу.
- UUID, credentials, содержимое dump и ключ архива не выводятся в публичный отчёт.
- Maven verify, Python suites, Starter/HTTP contract checks, секреты и расширенная
  локальная HTTPS/restore репетиция проходят. Реальные dev volumes не затрагиваются.

## Доступы, сроки и инфраструктура

В этой лаборатории данные только синтетические, собственные временные ресурсы
удаляются после проверки. Она **не задаёт production retention**. Автоматический
`forget/prune`, очистка receipts и расписание не входят в предложение.

До удалённого staging нужны отдельные решения:

| Решение | Что необходимо зафиксировать |
|---|---|
| Место хранения | Провайдер/сервер, регион, бюджет, отдельная от БД зона отказа |
| Доступ | Кто создаёт копии, кто читает и кто удаляет; защита учётной записи хранилища; хранение и восстановление ключа отдельно от исходной машины |
| Частота и потеря данных | Расписание backup и export, наблюдение за ошибками/устареванием; допустимая потеря обычных данных отдельно от неполной истории удалений |
| Сроки | Все действующие копии, exports, review, provider versions и временные файлы; история должна покрывать ещё восстанавливаемые backups |
| Приёмка | Извлечение после потери исходной машины, проверка списка удалений и измеренный полный RTO на выбранной инфраструктуре |

Нельзя удалять историю только потому, что её UUID старый, пока существует backup,
способный восстановить соответствующий аккаунт. Удаление snapshot через `forget`
не означает немедленного физического удаления его данных: у restic отдельный этап
`prune`, а удалённый provider может иметь собственные версии и сроки.

## Границы и остановка

- Локальные папки на одной машине не переживают потерю всей машины.
- Шифрование не предотвращает удаление архива субъектом с правом удаления.
- Утраченный ключ делает шифрованные копии бесполезными; управление ключом входит
  в будущую эксплуатационную политику.
- Периодический export оставляет неизвестный интервал при потере источника.
  Карантин B4.2 остаётся обязательным, а не автоматически снимаемым неудобством.
- Никаких новых серверных сервисов, изменений Starter/auth/mobile, API удаления,
  облачных ресурсов, платных операций, scheduled tasks и публикации.
- Существующие container security blockers, внешняя инфраструктура и M4 этим
  этапом не закрываются. Очередной локальный этап не означает готовность выпуска.

После локальной проверки — отчёт и остановка. Следующий шаг определяется выбором
реальной инфраструктуры и требованиями к восстановлению, а не автоматическим
добавлением очередного сервиса. Если вариант B сейчас не нужен, вариант A позволяет
сохранить проверенный B4.4 и вернуться к хранению после выбора инфраструктуры.
