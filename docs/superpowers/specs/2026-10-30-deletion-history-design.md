# B4.4: квитанции удалений и приватная выгрузка — предложение

Дата: 30 октября 2026. **Пользователь утвердил локальный вариант B и поручил реализацию.**
Пользователь поручил начать следующий этап; этот документ даёт конкретный вариант
для выбора до изменения хранения данных. Работа одним агентом, локально, без deployment.

## Зачем

B4.2 закрывает восстановленную БД до сверки удалений. Однако нынешний
`AccountDeletionService` не сохраняет UUID удалённого аккаунта: минимальный
`admin_audit` намеренно не содержит его. Оператору неоткуда автоматически получить
список. Цель предлагаемого B4.4 — собирать подтверждённые удаления и готовить
приватные файлы для существующей процедуры, сохраняя атомарное поведение API.

## Подходы

| Вариант | Сложность / затраты / сопровождение | Совместимость и ограничения |
|---|---|---|
| A. Существующий ручной список B4.2 | Минимум; новых компонентов нет | API прежний, UUID и полноту обеспечивает оператор |
| B. Квитанция в той же транзакции + отдельная приватная выгрузка | Небольшая миграция, JDBC и Python stdlib; без новых сервисов/библиотек/платных ресурсов | Сохраняет rollback/API; независим только уже выгруженный файл, есть окно потери невыгруженных записей |
| C. Отдельное хранилище с подтверждением доставки | Дополнительное хранилище, права, мониторинг и протокол восстановления после сбоев; стоимость зависит от будущей инфраструктуры | Надёжность выше только при проверенном протоколе; простая запись в две БД не атомарна |

**Рекомендация автора: B как ограниченный локальный этап.** A оставляет ручное
собирание UUID, C преждевременно вводит инфраструктуру и протокол доставки.
Пользователь выбрал B с указанными ограничениями. B не объявляется полноценным независимым онлайн-журналом.

## Предлагаемая реализация B

1. Новая Flyway migration V7 добавляет `hackatlas.account_deletion_receipt`:
   случайный UUID записи, UUID удалённого аккаунта и время записи. Без FK к аккаунту,
   email, password hash, токена, IP, профиля или текста обращений. Время записи —
   диагностическое; оно не считается точным временем commit.
2. После проверки пароля квитанция записывается в **ту же транзакцию**, что DELETE,
   каскады и минимальный audit. Ошибка любого INSERT/DELETE откатывает всё. После
   неуспеха нет ложной квитанции. `admin_audit` не меняет свою privacy-семантику.
3. Release runtime получает только INSERT на новую таблицу; SELECT/UPDATE/DELETE
   запрещены. Экспорт — отдельная read-only операция операторским соединением.
   В запросе удаления нет сетевой доставки, файловых side effects или нового сервиса.
4. `export_deletions.py` читает все зафиксированные квитанции одной согласованной
   snapshot-транзакцией и создаёт новый private JSON вне Git. Поля: версия,
   source project/database, UTC exportedAt, отсортированные уникальные account UUID,
   количество и явное указание, что глобальная полнота истории не доказана.
   Ограничения: до 10 000 UUID / 1 MiB; превышение — отказ без усечения.
5. Выгрузка полная: без фильтра по timestamp и без incremental sequence watermark.
   Раннее получение номера/времени не гарантирует порядок commit, поэтому такие
   отсечки могут пропустить поздно зафиксированную транзакцию.
6. `prepare_restore_review.py` проверяет private export, читает metadata конкретного
   quarantined target и создаёт **неодобренный** review формата B4.2. Project/database/
   backup hash/restoreId берутся из target; source identity остаётся в отдельном
   export для сверки и не добавляется в строгий девятипольный review B4.2.
   `sourceWritesStopped=false`, `deletionsReviewed=false`, `reviewedThrough=null`:
   оператор завершает действительную сверку, а не получает автоматически true.
7. Подготовка review не выдаёт CONNECT и не вызывает approve. Существующие строгие
   правила `approve_restore.py` остаются. Уже отсутствующий UUID допустим;
   повторная регистрация с новым UUID не удаляется по совпадению email.

Файлы — только Linux/WSL, regular file 0600 или строже, без symlink/FIFO,
duplicate JSON keys и неизвестных полей. Создание через exclusive open, fsync;
существующий путь не перезаписывается. CLI выводит состояние/счётчики, не UUID.
Внешний файл — псевдонимные данные, а не публичная диагностика или CI artifact.
Source экспортёр не принимает БД с restore marker за независимый оригинал.

## Граница гарантий

- Квитанция внутри той же БД **не независима от восстановления**. Неодобренная
  выгрузка/копия не служит доказательством полной истории.
- Потеря источника после последнего export оставляет неизвестный интервал.
  Без достоверного дополнительного списка target остаётся в карантине.
- Ранее выполненные удаления не восстанавливаются задним числом. Учёт охватывает
  только новый путь удаления после замены всех writers; ручной SQL/старые instances
  требуют отдельной сверки. Одна дата migration не доказывает начало полного учёта.
- Автоматическое удаление квитанций/exports не добавляется: retention должен покрыть
  действующие backups и быть согласован отдельно. Это не бессрочная production-политика.
- Выгрузка не шифруется и не переносится offsite автоматически; реальная инфраструктура,
  регулярная доставка, retention, RPO/RTO и доступы остаются условиями до реальных пользователей.
- Нет изменений Starter, opaque auth, mobile, публичных endpoints или текущего 204.
  Нет Kafka/Redis, общего outbox worker, distributed transaction или AFTER_COMMIT
  callback, выдаваемого за надёжное независимое хранилище.

## План результата после утверждения

Migration + атомарная запись → private export/review draft → интеграционные тесты
с настоящей PostgreSQL → локальная HTTPS/restore репетиция → документация и отчёт.
Подробный implementation plan составляется после выбора/утверждения дизайна.

Проверить успех/rollback/конкурентное удаление и повторную регистрацию, права runtime,
полноту snapshot при concurrency, отсутствие UUID/секретов в логах, private-file guards,
ошибочные export/target и неизменность карантина. Полный Maven verify и Starter/HTTP
checks обязательны; новые сценарии — на synthetic data. Существующие реальные БД
не мигрировать, commit/push/PR не выполнять. Контейнерные blockers B4.3 остаются открытыми.

## Проверенные основания

- [PostgreSQL 17 isolation](https://www.postgresql.org/docs/17/transaction-iso.html):
  snapshot isolation и особая, неоткатываемая семантика sequences.
- [pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html): согласованная копия
  допускает параллельных writers; сама по себе не фиксирует все будущие удаления.
- [Spring transaction events](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html):
  AFTER_COMMIT — фаза listener. Вывод автора: одно такое событие не заменяет
  сохранённую квитанцию и независимую доставку при остановке процесса.
