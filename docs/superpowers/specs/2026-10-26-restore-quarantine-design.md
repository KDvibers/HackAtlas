# B4.2: карантин восстановленной БД и операторская проверка удалений

Статус: утверждён пользователем 26 октября 2026 с поручением продолжить реализацию. Основа: main `fd6a6a18fcd3d014474403fe5195f888b9b88e6a`, B4.1 PR #11. Пользователь выбрал небольшую операторскую процедуру; внешнее размещение и автоматический независимый журнал удалений в этот этап не входят.

## Цель и границы

Старый backup может вернуть аккаунт, удалённый после его создания. Отзыв сессий не предотвращает вход восстановленного аккаунта по паролю. Сейчас `restore.py` выдаёт runtime CONNECT до privacy review — это нужно исправить.

Результат этапа: восстановленная БД остаётся закрытой для приложения до проверки и повторного применения подтверждённых удалений. Исходная БД не изменяется. Работа выполняется локально на синтетических данных; production-данные и внешний deployment не затрагиваются. API, opaque sessions, Java-логика удаления аккаунта и миграции остаются прежними.

## Рассмотренные подходы

1. **Операторская процедура с закрытым доступом — выбранный подход.** Небольшая доработка существующих ops scripts, без внешнего сервиса. Полнота списка удалений остаётся ответственностью оператора.
2. **Автоматический независимый журнал удалений — отложен.** Требует отдельного решения о надёжной записи, независимом хранении, согласованности удаления и сроках хранения самого журнала. Его нельзя заменять журналом из того же старого backup.

## Предлагаемая процедура

1. `restore.py` проверяет checksum, создаёт только новую `hackatlas_restore_*` БД, восстанавливает схему/данные, отзывает сессии. PUBLIC и runtime не получают CONNECT. Мигратор остаётся доступен для проверки схемы.
2. После успешного восстановления фиксируется состояние `QUARANTINED`, имя project/database, SHA-256 backup, уникальный `restoreId` и время восстановления. Хранение — структурированный comment новой БД: это deployment-local metadata без изменения схемы приложения. В него не записываются email, UUID удаляемых пользователей или содержимое обращений. Runtime не является владельцем БД и не может менять это состояние.
3. Оператор останавливает все источники записи исходного сервиса и сверяет удаления после snapshot по достоверному независимому списку/подтверждённым запросам. Если такого источника нет, БД остаётся закрытой.
4. Оператор готовит приватный review JSON: версия формата, project, database, backup SHA-256, подтверждение остановки записей и полноты сверки, время сверки, список UUID удалённых аккаунтов. Пустой список допустим только как явное подтверждение отсутствия последующих удалений. Пароли, токены и email в файл не включаются; в Git и CI artifacts он не попадает.
5. Новая `approve_restore.py` принимает этот файл. Проверяет формат, UUID, отсутствие дубликатов, совпадение project/database/hash и актуальность сверки относительно восстановления. Подтверждение полноты списка — ручное свидетельство оператора, не автоматически доказанная гарантия.
6. Под блокировкой одна транзакция повторно проверяет состояние карантина, удаляет только перечисленные UUID из восстановленной БД с существующими FK-каскадами, записывает минимальный аудит без персональных данных, повторно очищает сессии, сохраняет состояние проверки и выдаёт runtime CONNECT. SQL-ошибка откатывает изменения и выдачу доступа. При потере ответа после commit оператор проверяет state/ACL. Повторное одобрение уже открытой БД запрещено.
7. Только после успешного завершения оператор переключает приложение и выполняет smoke. Это разрешает проверку восстановленной копии, но не означает готовность публичного выпуска: container blockers и M4 сохраняются.

## Проверка результата

- Реальное подключение runtime к восстановленной БД до одобрения отвергается, включая случай повторного запуска мигратора.
- Отсутствующий, повреждённый, чужой или неполный review не открывает доступ и не изменяет аккаунты. Проверяются неправильные hash/project/database, UUID и дубликаты.
- Сценарий: backup двух синтетических аккаунтов → удаление одного через API → restore → карантин → подтверждённое повторное удаление → доступ разрешён. Удалённый аккаунт не входит; сохранённый аккаунт входит с новой сессией, старые токены дают 401.
- Принудительный сбой транзакции оставляет аккаунты и карантин без частичного применения; source DB fingerprints не меняются.
- Все проверки используют собственные disposable containers/БД. Реальные review-файлы не публикуются; отчёты содержат только состояние и количества.

## Что остаётся за пределами результата

Автоматическая полнота истории удалений, внешний журнал, расписание/offsite backup, выбранное хранилище, шифрование средствами провайдера и production retention не объявляются реализованными. В runbook фиксируются требования к этим решениям; конкретная инфраструктура и сроки хранения согласуются до deployment. Новые библиотеки и серверные компоненты не нужны: Python stdlib, PostgreSQL и существующий Compose.

Commit, push и PR выполняет пользователь. Реализация выполняется по [плану](../plans/2026-10-26-restore-quarantine.md), одним агентом в текущем checkout.
