# B3: удаление аккаунта и хранение данных

Техническое описание реализации на 26 октября 2026. Это описание поведения backend, а не опубликованная юридическая политика. Контракт — [OpenAPI](../api/openapi.yaml) и [API README](../api/README.md); настройка админки — [MODERATION](../backend/MODERATION.md).

## Что делает удаление

`POST /api/v1/me/delete-account` требует действующую opaque Bearer session и текущий пароль. Пароль проверяется без обрезания пробелов. Ошибка подтверждения возвращает 401, превышение лимита — 429. Успех — 204 без тела.

В одной транзакции удаляются аккаунт и профиль, password hash, все Bearer sessions, интересы, сохранённые события, личные отметки заявок, предложения и жалобы пользователя вместе с их свободным текстом, а также право доступа в админку. Параллельные login и новые личные связи согласованы блокировкой аккаунта: успешно удалённый аккаунт не получает новую действующую сессию. При сбое запись откатывается целиком; это проверено искусственной ошибкой аудита после DELETE.

Существующая браузерная admin session не является долгосрочным правом доступа: каждый запрос заново проверяет аккаунт и `admin_access`. После удаления или отзыва права следующий admin запрос отвергается и сессия инвалидируется. Уже выполняющийся запрос не отменяется задним числом.

Публичные карточки хакатонов не принадлежат удаляемому аккаунту и сохраняются. Повторная регистрация того же email создаёт новый UUID и пустой профиль; прежние личные списки не восстанавливаются. Клиент должен отдельно очистить собственные токены, данные аккаунта и кеш; backend не может физически стереть файлы на телефоне.

## Аудит и логи

`admin_audit` хранит UUID записи, действие, время, необязательные UUID оператора и события. После удаления оператора его `actor_id` становится NULL. Запись `ACCOUNT_DELETED` изначально не содержит actor ID, email, profile ID, IP, пароля или текста обращений. В аудит не копируются формы, тела запросов, ссылки предложений или их комментарии. Оставшиеся время и действия не следует считать гарантированно анонимными при сопоставлении с внешними источниками.

В штатных обработчиках ошибок логируются request ID и классы исключений; API также сохраняет SQLState для диагностики. Пароли, Bearer tokens, SQL и значения строк не выводятся. Категории Hibernate JDBC error, Spring transaction override и Hikari ProxyConnection, способные выводить полные сообщения драйвера, выключены в базовой конфигурации. Остальное логирование сохраняется; тесты проверяют отсутствие секретных маркеров БД при ошибках 500/503. Изменение logging levels, внешние proxy/access logs и инфраструктурный сбор логов требуют отдельной проверки перед deployment.

## Лимиты и сроки хранения

Auth и moderation rate limiter хранят в памяти процесса SHA-256 ключи IP/email или UUID аккаунта и счётчики. Это псевдонимизация, а не гарантированная анонимизация. Окна по умолчанию — 15 минут для auth и 1 час для модерации. Просроченные ключи удаляются при повторном обращении к ключу или заполнении ёмкости, все ключи исчезают при рестарте. Фоновая очистка по таймеру и удаление ключей конкретного аккаунта не реализованы; жёсткий срок физического удаления из памяти не заявляется. Ёмкость каждой таблицы ограничена 10 000 ключей.

В private DEMO фиксированный Clock останавливает и эти окна, и срок сессий. Для длительной проверки auth/лимитов используйте реальные часы или перезапустите изолированное dev-окружение. Production запрещает DEMO Clock.

Обработанные обращения сохраняются до удаления аккаунта или отдельно согласованного обслуживания БД; перевод в RESOLVED/DISMISSED только убирает запись из очереди. Автоматический срок очистки обращений и audit log в B3 не установлен и не реализован.

## Резервные копии и подготовка B4

Удаление применяется к текущей рабочей БД. Внешние backups и production не развёрнуты; стирание уже существующих снимков инфраструктуры не гарантируется. Локальный Compose volume сохраняет данные после остановки PostgreSQL.

В B4/B4.2 добавлены [backup/restore helpers](../infra/release/README.md): private custom-format dump с checksum, восстановление только в новую БД, отзыв всех восстановленных Bearer sessions и **карантин без runtime CONNECT**. Исходная БД не перезаписывается. Старый snapshot всё ещё содержит строки и password hashes аккаунтов, удалённых позже; до операторской сверки `readyForSmoke=false`, `requiresPrivacyReview=true`.

Оператор останавливает все writers и сверяет удаления после snapshot по достоверному независимому списку/подтверждённым запросам. `approve_restore.py` принимает приватный review, связанный с project/database/hash/restoreId, и атомарно удаляет перечисленные UUID через существующие каскады, пишет минимальный audit без user ID, повторно отзывает сессии и открывает runtime CONNECT. Ошибка не оставляет частичного открытия. Подтверждения и время сверки проверяются; полноту списка оператор подтверждает вручную. Metadata/state содержат только идентификатор попытки, hash, timestamps и количества, без списка удаляемых UUID. Сам review-файл содержит псевдонимные UUID, защищается Linux permissions и не публикуется в Git/CI.

При отсутствии достоверного списка восстановленная копия остаётся изолированной. Автоматический независимый журнал и доказательство полноты истории не внедрены. `admin_audit` не позволяет получить список UUID удалений, поскольку ACCOUNT_DELETED их не сохраняет. Одобренный локальный review не означает автоматическое стирание старых backups, физическое удаление всех копий или готовность production privacy. В синтетическом тесте повторно удаляется известный UUID; реальные запросы требуют достоверной внешней процедуры.

Сроки хранения логов, обращений, аудита и backups, offsite-шифрование, расписание и контроль успешности backup остаются обязательными решениями перед внешним deployment. Локальный release-кандидат ограничивает размер Docker logs и удаляет поле request из Caddy runtime logs; это ограничение размера, а не согласованный срок retention. Подготовка B4 не объявляется публичным выпуском или готовой юридической политикой.
