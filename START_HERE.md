# С чего начать вам двоим

## Это уже сделано в комплекте
Два подробных Codex-промпта, общие AGENTS.md, правила стиля, утверждённое фото, API-контракт с fixtures, этапы и GitHub-процесс. Локально реализованы основа backend B0 и публичный каталог B1. Авторизация B2 и мобильная реализация остаются отдельными этапами. Старые HTML/Figma-файлы не использовать как основной эталон вместо фото.

## 1. Существующий общий GitHub-репозиторий
Репозиторий уже создан: [KDvibers/HackAtlas](https://github.com/KDvibers/HackAtlas). Его первоначальная история сохранена. Повторный `git fetch origin` 20 октября подтвердил merge B0 в `origin/main` (`43b11e4`, PR #2); B0 commit — `208e097`. B1 подготовлен поверх B0 в `feat/catalog-api`, база PR — `main`. Commit, push и PR B1 выполняет пользователь.

В существующем клоне не повторять `git init` и не распаковывать ZIP поверх изменений. Для новой машины:

```bash
git clone https://github.com/KDvibers/HackAtlas.git
cd HackAtlas
git status --short --branch
```

У каждого разработчика свой аккаунт и локальный клон. Для серверной работы используется GitHub-аккаунт `yergaliuly`. GitHub handle напарника пока не указан; не подставлять случайный аккаунт в CODEOWNERS.

Единственный актуальный комплект — Starter. Правила авторизации: opaque Bearer sessions по `api/`, без JWT и refresh endpoint. См. [решения](docs/DECISIONS.md) и [результат аудита](docs/SETUP_AUDIT.md).

Перед новым этапом оба разработчика читают [PROJECT](docs/PROJECT.md), [TECHNOLOGY_DECISIONS](docs/TECHNOLOGY_DECISIONS.md), [общий ROADMAP](docs/ROADMAP.md) и статус своей части. Исследование сохраняет варианты; принятые технологии и условия выбора зафиксированы отдельно. Проверяйте ветку, из которой друг получил документы и код: доступность feature-ветки не означает её включение в main.

## 2. Твой Codex
Открой локальный корень HackAtlas, прочитай `docs/STATUS_BACKEND.md` и `prompts/BACKEND_CODEX.md`. Промпт описывает B0+B1, но границу работы задаёт текущий запрос пользователя. B1 реализован локально; [запуск и проверки](backend/README.md) доступны в репозитории. Следующий отдельный этап — B2, без автоматического перехода. При повторном входе опирайся на статус и существующий код.

## 3. Codex друга
Друг открывает свой clone того же репозитория, прикрепляет утверждённое фото и вставляет **полный текст** `prompts/MOBILE_CODEX.md`. Он запускает M0+M1: cross-platform каркас и три главных экрана на общих fixtures. После проверки внешнего вида остановиться на утверждение, а не автоматически делать остальные экраны в неправильном стиле.

## 4. Что можно делать параллельно
Ты проверяешь и публикуешь B1, друг делает визуальное ядро на fixtures. Обоим доступны один API и одна картинка. Готовность B1 не зависит от завершения его дизайна; M1 не зависит от запущенного сервера.

После B1 отправь другу сообщение из отчёта Codex, сделай PR и merge с проверками. Друг обновляет main и подключает remote repository, сохранив UI. Переход к auth только после согласованного этапа.

## 6. Важные ограничения
iOS build/device verification требуют подходящего Mac+Xcode; kit не создаёт к ним доступ. Нет Mac — Android/common можно делать, но iOS остаётся непроверенным до реального запуска. Публикация новых изменений остаётся за пользователем. Файлы шрифтов не приложены, точный шрифт фото не установлен. API — исходный договор, не доказательство готового endpoint.
