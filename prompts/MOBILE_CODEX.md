## 2. Что это за продукт

HackAtlas — каталог хакатонов: посмотреть будущие события, найти подходящие по теме/формату/городу, прочитать сроки, требования и призы, сохранить, открыть официальную регистрацию. Начальный охват — Казахстан и подходящие international-online события; «все хакатоны мира» не обещаем.

Просмотр без аккаунта. У гостя локальные сохранения; у вошедшего пользователя они синхронизируются с Java API. Профиль пока не публичная социальная страница. Поиск тиммейтов будет позже: сейчас не создавать команды, чат и social feed.

Четыре вкладки как в фото: Главная / Календарь / Сохранённое / Профиль. Календарь сначала показывает сохранённые события и deadlines. Не менять на три вкладки из старого обсуждения. На detail back и закреплённый CTA.

## 3. Стек и структура

Общие UI и логика — Kotlin Multiplatform + Compose Multiplatform. Android и iOS — отдельные сборки одного общего проекта. Не заменять на Flutter, React Native, сайт, WebView или две независимые реализации Kotlin/Swift. Swift допустим как небольшой iOS host/platform bridge, но не как повтор всех экранов.

Структура по умолчанию:
- mobile/shared: commonMain UI/state/domain/repositories/DTO; androidMain/iosMain платформенные адаптеры;
- mobile/androidApp: Android host;
- mobile/iosApp: Xcode host;
- mobile/gradle/libs.versions.toml и собственный Gradle wrapper.

Если существующий официальный совместимый шаблон использует другое имя shared-модуля, сначала объясни минимальную адаптацию; не перестраивай рабочий репозиторий ради названия папки.

Ktor Client, kotlinx.serialization, coroutines/StateFlow, common date/time API, совместимый multiplatform navigation/lifecycle. OkHttp engine Android, Darwin iOS. Coil 3 для сетевых картинок при необходимости. Ручной constructor DI сначала достаточно. Небольшие несекретные настройки и guest-saved — через Settings abstraction (например, multiplatform-settings), а не отдельную тяжёлую базу без нужды. Не хранить токены в обычных settings.

Сначала проверь официальную совместимость Kotlin/Compose/Compose compiler/Gradle/AGP/JDK/SDK/Xcode и зафиксируй точные stable версии в mobile/TOOLCHAIN.md и version catalog. Не использовать alpha/beta/EAP/SNAPSHOT, динамические '+', разные несовместимые примеры. Зафиксируй min/target SDK и iOS deployment target после проверки, не заявляй поддержку всех старых телефонов.

На Windows можно делать Android/common. Для реальной iOS сборки нужен Mac+Xcode; проверь доступность и архитектуру. Если их нет, подготовь host/инструкцию и честно обозначь непроверенность. Не удаляй iOS цель, не называй подготовленный код проверенным iOS приложением.

## 4. Самое главное: визуал нельзя уводить от фото

Нужен именно показанный чёрно-фиолетовый neon hacker/cyber-tech стиль. Не просто «dark theme с фиолетовым primary». Сохрани:
- почти чёрный фон;
- яркую фуксию/магента-кнопку с локальным glow;
- тонкие фиолетовые outlines тёмных карточек;
- немного cyan;
- крупные пиксельные названия «Хакатоны», «Профиль» и tech-акценты;
- обычный чёткий текст в описании и полях;
- wireframe/point-cloud голову, city skyline, controller как отдельный арт;
- контурные иконки одного набора;
- компоновку трёх экранов и активные pink tabs из reference.

Запрещено: стандартный вид Material 3, dynamic color, пастельный/светлый редизайн, глобальное упрощение, огромные округлые карточки, emoji-иконки, обычный sans вместо пиксельных заголовков, generic blobs вместо wireframe, бесконечные glitch/падающий код.

Используй design/tokens.json как начальные приближения. Точное соответствие оценивается по фото и скриншотам, а не только по hex. Сначала создай HackAtlasTheme, PixelHeading, TechLabel, NeonButton, NeonOutlinedField, HackathonCard, HackathonMiniCard, InfoItem, InterestChip, HackAtlasTabBar, WireframeDecoration и состояния этих компонентов. UI не должен состоять из одного огромного composable.

Точный исходный шрифт не предоставлен: не утверждай, что знаешь его название. Подбери лицензируемый display с кириллицей и покажи реальный образец «Хакатоны / Профиль / Сохранённое / Й / Ё». Для статичных wordmarks можно сделать доступный вектор, но не для динамических текстов. Если шрифт/ассет пока отсутствует, запиши blocker в design/assets/MISSING.md, не объявляй случайную замену финальной.

Референс не надо вставлять в приложение целиком. Кнопки, текст, метаданные, карточки — настоящие компоненты с кликами и доступностью. Внешний корпус телефона, notch, fake 9:41 и рекламные подписи вне телефона не являются частью app UI. Декоративные сетки не должны затруднять чтение.

В первом проходе сделай три экрана: каталог, detail и профиль. Сохрани положение блоков и визуальную иерархию. Рабочий viewport ориентировочно390×844; адаптация320–430 logical width, safe areas и large text важнее буквального масштаба png. Не уменьшать текст ради совпадения с промо-картинкой. Обычный body около15–16, touch targets по платформенным требованиям, animations short/reduced-motion.

## 5. Данные и API

Канонический контракт уже находится в api/openapi.yaml + README. Не создавай свой endpoint или DTO с другими названиями. Не редактируй API и backend без согласования. Если отсутствует необходимое поле — отдельный contract change request другу, а не тихая переделка.

Первые adapters: HackathonRepository, ProfileRepository, SavedRepository; также PlatformBrowser, SecureTokenStore, LocalPreferences, CalendarExporter/ReminderScheduler по мере этапов. UI работает с state/models, не с JSON и network calls внутри composable.

В M1 DemoRepository читает общие fixtures api/examples, а не собственные массивы в каждом экране. REMOTE adapter позже использует те же DTO и mapping. DEMO выбирается явно; в release он отключён. Ошибка REMOTE никогда не заменяется fake success или переключением на demo. Fixture clock фиксирован; даты не превращаются в якобы актуальные события.

Public endpoints: GET /api/v1/hackathons, /hackathons/{id}, /metadata/filters. Search debounce и отмена предыдущего запроса, pagination, безопасная enum обработка, loading/error/empty/retry. Не терять filters и scroll при возврате с detail.

После B2: register/login/logout, GET/PATCH /me, GET /me/saved, идемпотентные PUT/DELETE /me/saved/{id}, GET/PUT/DELETE личных application marks. Auth — opaque bearer token по контракту, не JWT и не выдуманный refresh endpoint. SecureTokenStore: Keychain iOS / защищённое Android-хранилище с Keystore. Авторизацию отправлять только своему API origin; не переносить Bearer на organizer URL, сторонние image URLs или share intents.

На401 очистить недействительную сессию, сохранить пользовательский незавершённый сценарий насколько возможно, предложить войти. Guest saved импортировать в аккаунт после согласия, без потери неподтверждённых сервером закладок. Данные разных аккаунтов разделять; logout не делает account saved общими.

Base URL через окружение. Для телефона localhost не означает ПК. Составь точную инструкцию Android emulator/реальный Android/iOS simulator/iPhone/LAN/staging под фактическое окружение. HTTP только debug; release HTTPS; не отключать проверку сертификатов.

## 6. Смысловые правила интерфейса

Дата начала и registrationDeadline — отдельные подписи. Unknown deadline/time не заполнять 23:59. Prize unknown не показывать как0. Общий фонд не называть выигрышем одного участника. Online не означает допуск из любой страны.

«Перейти к регистрации» открывает официальный HTTPS сайт системным browser surface: Android Custom Tabs, iOS SFSafariViewController либо безопасный платформенный browser fallback. Не встроенный произвольный WebView с собственным логином. Подписать переход к организатору. Проверять null/closed/cancelled states.

Нажатие URL не значит, что человек подал заявку. Предлагать необязательное «Я подал(а) заявку», self-reported. Не рисовать «Вы приняты» без интеграции с организатором.

Статистика из референса демонстрационная. Для настоящего профиля показывать только правдивые значения; сохрани трёхколоночную компоновку, но не выдумывай победы. Guest profile не выдавать за существующий аккаунт.
